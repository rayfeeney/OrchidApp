The previous script used fixed personal paths, retained remote SQL for 14 days and mirrored only current uploads. Those separate histories could not establish historical photo recovery. It also logged before creating its directories and depended on an implicit scheduling account's rclone/client settings.

## Implementation

The Bash entry point now delegates to a shared Python standard-library implementation with explicit protected JSON, client-defaults and rclone configuration. A matching restore entry point is added. Each versioned archive contains SQL, the complete uploads/configuration trees, hashes and active photo references. Empty/hidden files survive. Manual or scheduled writer control and a persistent server-wide read lock cover capture; file/reference changes prevent completion. Scheduled mode restarts only previously active units, preserving inactive state and reporting restart failures.

New archives are verified locally, copied immutably and downloaded for hash comparison before local pruning. Retention validates exact-pattern same-collection files; pinned, unknown, foreign and corrupt inputs remain. Restore pins local inputs before mutation, validates safe archive entries and requires an existing empty same-name database on an operator-confirmed isolated server. It stages new uploads/settings without overwriting existing paths. Failed imports retain RESTORE-PENDING.json and explicitly allow partially applied DDL. Configuration is staged for private review, not activated. There is no automatic cloud deletion, legacy conversion, schema change or Windows behavior change.

## Validation and limits

The final local run discovered 31 tests: 28 passed, with three explicit skips (POSIX permissions, source symlink creation and the actual rclone crypt backend). The executed set includes the native canonical-schema MariaDB integration. Both Bash wrappers passed syntax checks using installed Git Bash; changed PowerShell parsed without errors and actionlint passed with optional ShellCheck/Pyflakes integrations disabled. No application build was needed for these script/documentation-only changes.

Local disposable archive/policy checks cover malformed/corrupt archives, traversal/links/duplicate entries, resource limits, empty/hidden files, historical photo bytes, required photos, private/explicit configuration, invalid values, stop/restart order, restart failures, retention exclusions/pins, changed capture files, failed upload/read-back and restore confirmations. Source symlink creation, POSIX modes and actual rclone crypt checks require the corresponding host capabilities; skipped cases are identified in test output.

The native MariaDB integration creates a generated database through the production canonical schema/seed creator with no migration replay. On a new private Windows MariaDB 10.11.16 instance it captures/restores rows, plant/taxon photos/thumbnails, hidden uploads and settings; an older archive retains its old row/photo values after newer source writes. A second SQL writer remains blocked while the actual read-lock connection exists. Missing active photos cannot produce a new completed archive. An intentional failing DDL fixture leaves partial SQL and the recovery marker/input. Generated databases are dropped and the owned server is shut down. No live collection or private environment file is used.

That local integration calls the shared implementation on Windows with simulated service/cloud adapters: it is not a Linux installation or real provider test. The Linux CI job installs MariaDB client/rclone, checks both Bash wrappers, runs the generated canonical-schema integration and an actual rclone crypt round trip against disposable local storage. Those new Linux steps still require a GitHub Actions run. Real systemd/cron account permissions, provider authentication/storage, Pi hardware, compatible application startup/save/reopen and whole-machine replacement acceptance remain pending. A functioning Docker Linux engine was unavailable locally; no Linux/Pi success is claimed.

The maintained [runbook](../user-guides/linux/OrchidApp-MariaDB-Backup-and-Restore-Runbook.md), installation prerequisites, full pre-upgrade guide, documentation map/index and contributor checks are updated. Existing Linux Word plant/first-use guides do not describe these scripts or backup commands, so no Word edit/render was required. Historical release runbooks are preserved unchanged.

## Operator boundary

All writers outside configured units must also be paused; hash comparisons do not prove no transient filesystem write was made and reverted. The global read lock affects other databases on that server. Service restart is not application readiness. Cloud retention and encryption/provider configuration remain operator responsibilities, and hashes are not authenticity signatures. Backups stage secret configuration: protect output/diagnostics and retain keys separately. Allow temporary space for verification. Interrupted operations can leave stopped units/stale locks; inspect before clearing them. Never retry failed DDL blindly or test restoration on a collection server.
