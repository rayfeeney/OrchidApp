# Historical Linux ARM64 package, application and recovery acceptance

Implementation date: 28 October 2026. Local end-to-end acceptance passed on 28 October 2026, 20:45–20:56 UTC; extended hosted CI remains to be run after this delivery is merged. This extends the already merged/passed historical database workflow, using the same published immutable specimen. It is automated container acceptance, not real Pi/systemd, browser JavaScript, cloud-provider or Windows installer acceptance.

## What actually runs

The maintained `scripts/package-linuxpi.ps1` builds two complete self-contained Linux ARM64 ZIPs from the reviewed source. `-NoVersionStamp` suppresses prompts/source version writes, `-OutputRoot` selects a new absent directory, and `-InformationalVersionOverride` gives the builds different compiled identities. These two test builds have the same functional source and migration set; the app-only case demonstrates binary replacement without SQL, not compatibility with every arbitrary release. Publish failure stops packaging; existing explicit output is preserved. Default interactive packaging still stamps/increments the normal release version.

The test verifies complete safe package inventories, packaged migration/backup bytes and package hashes. A pinned ARM64 .NET 8.0.33 Bookworm image with libvips42 8.14.1-3+deb12u3 runs the historical and current application as UID 1654. Other installed tool versions, image IDs and package hashes are recorded. Debian tool dependencies can change; this is not a bit-for-bit Pi OS image. The test database remains pinned Linux amd64 MariaDB 10.11.14. The application shares its network-none namespace; no port or host filesystem is mounted/published. Docker/QEMU runs the actual ARM64 binaries on an amd64 host.

## Phases and proofs

1. Verify the outer specimen, all 1,073 member hashes, synthetic uploads, original 245-row ledger and table counts. Extract only verified runtime files for the application phase. Start the original captured build, check five core pages and an existing photo's HTTP bytes, then stop it.
2. Use the actual packaged production `orchid_backup.py` to capture the original database, full uploads and external configuration under a real held database read lock. Its archive validation and real rclone crypt copy/read-back run against private local storage. Save/verify the matching old application tree separately to complete the recovery set.
3. Execute the established exact structural admission/audit-ledger rollover, four canonical forward migrations, zero-work second apply, unchanged pre-workflow data and exact final schema checks. No historical migration replay or checksum-policy relaxation occurs.
4. Deploy the current ZIP's app tree while preserving external uploads/settings. Verify core pages, current readiness and an existing photo. Execute 17 real HTTP-form checks with antiforgery/session handling: create an independent parent; growth/bloom quick actions; note; photo plus note with saved JPEG/thumbnail bytes and dimensions; movement and closed prior location; completed/open/finished flowering and reports; repotting and reopen; selected validation failures; split exactly two children with permanent tags, media, initially absent locations, parent closure and lineage. Confirm migration history is unchanged by application actions.
5. Stop/restart the app and compare all database data, metadata, upload bytes and configuration. Capture a second actual paired backup plus the matching current application tree before app-only replacement.
6. Deploy the distinct second compiled package, require readiness/core pages, and prove the complete database data/schema/ledger, uploads and settings are unchanged before test writes. Create/save/reopen a dedicated test plant/note. Stop it, remove its main DLL deliberately, and require the broken package to fail startup.
7. Provision the known isolated database empty and invoke the production restore CLI with its exact database/isolation confirmations. It pins/validates the input and stages files/configuration. Activate only the staged matching fixture files and saved current app. Verify all pre-app-only database data/schema/history and every upload/setting/app byte match before further test writes; require readiness, core pages, a photo, and actual save/reopen.
8. Through the unchanged canonical migration runner, execute a generated test-only forward SQL file that creates a witness table then raises an error. Verify the actual partial DDL and durable pending checksum remain, and a subsequent PlanOnly refuses the incomplete state. Do not delete a marker to retry.
9. Recover the complete original pre-upgrade app/database/uploads/configuration set using the verified production paired restore and saved historical app. Exact original schema/history and all snapshot data/files/configuration must match before test writes. Start that compatible old build, check core pages/photo, and create/save/reopen a dedicated recovery plant/note. No current migration is replayed into the failed state.
10. Collect bounded reports/logs and remove only the identity-verified owned containers/volumes. Cleanup failures fail acceptance.

The deliberate database replacement in recovery is permitted only inside the newly owned disposable fixture; neither orchestrator nor driver accepts a live endpoint. The in-container driver additionally requires its matching ownership token/file. Unknown input, drift, partial staging, exposure or missing evidence fails rather than skipping a phase.

## Service and storage boundary

The production backup/restore CLI and database read lock are real. A fixture-only `systemctl show` adapter derives stopped/running state from the actual app child PID; no real systemd, scheduling account, timer/importer or cloud account is exercised. The app is stopped and reaped before capture/recovery/replacement. Real rclone crypt is backed by an isolated local directory, not a provider. Runtime/admin fixture accounts are provisioned explicitly; production account/permission restoration remains separate.

Docker overlay filesystems can reject renaming image-layer directories. The harness first fully stages/verifies replacement files; if retirement cannot be renamed, it copies/verifies the owned prior tree before removal. Writers remain stopped. This is fixture deployment orchestration, not a new production atomic deployment guarantee. Interrupted fixtures are discarded/restored, never force-repaired. Backups/private logs/runtime trees and package ZIPs are not uploaded as CI diagnostics.

## Issues found by this acceptance

**CHAT-R12: false photo recovery after a no-photo save.** The pre-fix ARM64 package saved a new plant, then `PhotoWriteBatch.Committed()` tried deleting a journal whose parent directory had never existed. Its cleanup handler created an empty `CommittedCleanupRequired` record, causing a later legitimate photo upload to be refused. `Track` with no files and commit/rollback with no tracked photos now resolve without journal I/O. Actual photo failures, uncertain transactions, cleanup errors and existing unresolved records retain their original recovery safeguards. No migration/setting or automatic journal cleanup is introduced.

Five new native regression assertions cover no-photo commit/rollback, subsequent real tracked-photo commit, and empty tracking lists. The full existing native suite passed locally: 611 metadata/orientation/colour checks plus 37 pair/transaction recovery checks on Windows libvips 8.18.2. NuGet emitted NU1900 for unavailable vulnerability metadata; that is not a completed security audit. The pre-fix ARM64 HTTP suite reproduced the blocked photo; the corrected package passed all 17 action checks.

**CHAT-R13: Linux package CI/reliability gaps.** Version prompting prevented unattended builds; a failed native `dotnet publish` was not checked before packaging continued. The new opt-in non-stamping build path and explicit exit check address these. Three package policy checks prove failure produces no ZIP, an existing explicit output/witness survives and tracked version properties remain unchanged. No new production version is stamped by CI.

## PR #362 hosted shell-exit correction

The first merged-resolution PR run passed six jobs but stopped the feature job after the packaging policy script printed all three checks passed. The test's intentionally mocked native failure left LASTEXITCODE=42, which GitHub's PowerShell wrapper treated as a failing step. The feature runner therefore never executed, making the later missing artifacts/feature-checks error secondary. The punycode warning was not the cause.

The policy test now removes its mock through the correct Function provider path and resets LASTEXITCODE only after all assertions and cleanup succeed. A real assertion/cleanup exception still fails. Local validation reproduced the old behavior through the CI-style dot-sourced wrapper, then verified success returns zero and the mock does not leak; a deliberately failing assertion still returns nonzero. This correction does not weaken the evidence uploader's missing-file check or change production/application behavior. Hosted checks must be rerun on the correction commit.
