# C11 manual plant closure

## Change and upgrade action

Migration **202610261200_AtomicManualPlantClosure.sql** replaces only spUpdatePlantDetails. It corrects flowering.endDateTime to flowering.endDate and makes the plant/details, first location closure and first flowering closure atomic. A standalone call owns/commits its transaction; a call inside an existing transaction uses the reserved orchidapp_update_plant_details savepoint and does not commit prior caller work. SQL failures roll back the operation and rethrow the original error. MariaDB deadlocks can abort an entire caller transaction; this procedure does not override engine deadlock semantics or establish C13's broader concurrency guarantees.

The current calendar-date checks, unknown acquisition support, existing time preservation, split-child acquisition/split-parent end protection and ended-plant UI policy remain. Initial closure must be at/after open flowering starts and strictly after open location starts. Already closed intervals are unchanged. As in the old procedure, all open rows for that plant are included, even inactive open rows. Clearing/changing a previously set end date through direct procedure calls does not reopen/rewrite prior intervals; the current Edit page still refuses already-ended plants. C12 owns broader lifecycle correction policy.

Existing Windows Desktop installations apply the migration through their normal preflight/backup gate; Linux/manual administration uses PlanOnly then the canonical runner with explicit credentials and an operator-provided recoverable backup. Do not apply by hand and then also run it through the migration ledger. Fresh installations use the regenerated canonical schema and new baseline without migration replay. No new configuration setting is required. Both platform action lists are in the [upgrade checklist](../upgrade-checklist.md).

### Development checkout before committing

Stop the development app, run `pwsh ./scripts/DevSetup/update-database.ps1` from the repository root, then retry the commit. The update command and pre-commit export wrapper read the credentials already in the repository `.env`; no repeated terminal credential setup is needed. The update command plans, makes a SQL backup outside the repository and applies pending migrations through the canonical runner. `-PlanOnly` is available for preview. Normal dotnet run does not migrate, and the hook never migrates automatically. The export guard still refuses pending/older history before writing files. Do not bypass the hook or point this development workflow at a collection database. Direct deployment/administration runners retain their explicit configuration. See [development setup](../development-setup.md).

The migration does not modify plant data. Old versions could save a plant end date and then fail while closing flowering. On first adoption, after a verified backup, run the read-only [Review-ManualPlantClosure.sql](../../database/scripts/Review-ManualPlantClosure.sql) against the explicitly selected collection database. Its first result lists ended plants with active open location/flowering records; its second lists active intervals with invalid end/start order. Returned rows require investigation and can reflect other historical operations; the query is not a proof of cause or a repair script. Review the plant history, dates, lineage and trusted pre-failure evidence before agreeing a correction. Do not bulk assign end dates, reopen plants or bypass Edit restrictions. Preserve the report privately and track unresolved records separately. No retrospective repair is automated by C11.

Read-only inspection found that same cutoff in the owner's local checkout, while the original C11 delivery contains 202610261200. This establishes stale source artifacts, not a failure of the migrated procedure. Export from an unmigrated development database is a consistent explanation; the actual commit history was not inspected.

Restore the three matching generated artifacts from the correction delivery: database/schema/routines/spUpdatePlantDetails.sql, database/schema/bootstrap.json and database/checksums/schema.json. Do not change only the cutoff or relax the test. The subsequent `.env` follow-up provides the single development update command above, including its automatic SQL backup; use it, then retry the normal commit with its hook enabled.

Schema-ExportPreflight.ps1 now uses the canonical migration-history policy before exporter writes. Pending migrations, incomplete/malformed history, changed applied checksums and source cutoffs newer than recorded DB history are refused. Matching fresh baselines and valid schema-only export sources remain supported. Missing migration folders cannot bypass the source-cutoff comparison; a source with a migration folder must retain the applied files required by the existing policy. The guard does not prove arbitrary manual DB changes are semantically correct, and export itself is not made transactional by this change.

Twelve policy checks cover rejection/acceptance cases. The native integration stages a current source copy over the genuine prior-procedure DB, checks that refusal preserves every schema/checksum byte, then verifies successful export after applying C11. The fresh-schema diagnostic now prints the actual cutoff and asks for all matching generated files before importing. Linux CI still requires rerunning on the corrected commit.
