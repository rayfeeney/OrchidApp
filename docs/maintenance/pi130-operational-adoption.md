11 November 2026 candidate, based on `bcc4e7d`. Live use is **not yet accepted or approved**. The installed Linux procedure remains in [Step 4 of the Linux guide](../user-guides/linux/installation-upgrade.md#historical-pi-1-v130-ledger-adoption).

`database/scripts/adopt_pi130.py` is a separate source-checkout maintenance command. It imports the existing exact metadata validator and reads the existing versioned review contract. It neither imports nor invokes `legacy_adoption.py`; that tool retains its disposable-fixture scope and ownership guards. The reviewed JSON's canonical SHA-256 is pinned to `df128c98d01f60129251c3d38e04edb6ae6c5a1faa4ebcb460f6baf5c17c3fb6`. A different contract requires a source review. The new baseline checksum identifies a separate operational contract containing that review digest and the 245-row preservation requirement.

Only database `orchids`, MariaDB 10.11, a local Unix socket and authenticated `root@localhost` with global `ALL PRIVILEGES` are admitted. The command requires Linux root for operational execution. It loads no `.env` or client defaults, accepts no TCP endpoint, and disables native reconnect. Password-protected root accounts use the explicit `--ask-root-password` terminal prompt. It refuses empty input and echoing/noninteractive fallback; the supplied password is sent only in the native child environment, never arguments, files, journals or logs. Parent/ambient credentials are not reused or changed. The database account, privileges, local transport and approval requirements remain unchanged. An advisory lock remains on one native session throughout the operation. No dependency or migration-runner policy changes are required.

Before any database write, exact historical schema and ledger identity, target/account/version/socket, the four forward migration names and current file hashes, approval/recovery evidence, every declared stopped/masked writer unit, server `read_only=ON`, disabled event scheduler and absence of other sessions must pass. These maintenance conditions are rechecked before the table swap. The original ledger and schema are rechecked too. Metadata comparisons retain definers, creation context, column types, collations, index names, routines, views and complete object inventory. No tolerances are added for production.

The root-owned private approval file binds the observed target, operational contract, forward inventory and recovery-archive digest. The archive is hashed locally. Restoration success, off-device verification, complete writer inventory, scheduler isolation and administrative access isolation are explicit operator attestations with evidence references; the command cannot independently prove them. Stopped services and read-only mode alone cannot exclude another privileged administrator. Isolate that access for the maintenance window. No service, grant, scheduler or global setting is changed by the command.

An exclusive private journal directory records durable intent before DDL. The command creates `_schemaversion_adopting_pi130` using the existing ledger structure and inserts the recognised baseline marker. One MariaDB atomic multi-table `RENAME TABLE` preserves the original as `schemaversion_legacy_pi_130` and activates the staged ledger. All 245 original version IDs, HEX-encoded names/checksums and timestamps must match the pinned original history digest after the swap. The active marker and both ledger structures are verified separately. The tool performs no application-data SQL or forward migration.

## Interruption states

| Observed state | Meaning and action |
| --- | --- |
| Original ledger only, exact schema/history | No swap observed. A local intent journal still requires review; absence of staging does not authorise blind retry. |
| Staging table present | Interrupted or unreviewed staging. The tool refuses apply and leaves every object intact. |
| Original archive plus exact active baseline and exact structures | Swap completed and read-only verification passes. A missing `verified.json` means the process did not durably record success; reconcile journal, approval and database before proceeding. |
| Different ledger, missing objects, pending marker or modified schema | Refuse and investigate. Forward migrations change the active ledger, so adoption inspection after migration also refuses rather than certifying an unreviewed state. Use the canonical migration plan and recovery evidence. |

SIGTERM, KeyboardInterrupt, native failure, timeout and lost response preserve the journal and any created database objects. SIGKILL/power loss cannot write a final status. Connection disposal releases the advisory lock. There is no drop, rollback, retry, force, staging cleanup or pending-marker removal option. MariaDB atomic rename and the retained ledger distinguish pre-swap and post-swap states; this is not a claim that all DDL rolls back. Restoration uses the separately verified matching app/database/uploads/configuration recovery set.
